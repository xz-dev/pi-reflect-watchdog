## Why

A `NO_ISSUE` reflection currently ends without returning control to ordinary work, even when work remains. Pi converts custom messages to `user` messages and drops their metadata before model delivery, so reusing the correction handoff unchanged would also erase the required distinction between automatic and manually requested feedback. Automatic reports need assistant-role delivery; reports generated by a user's manual `/reflect` command must deliberately be delivered with the user role.

## What Changes

- **BREAKING behavior change:** both valid `NO_ISSUE` and `ROUTE_CORRECTION` results return control through exactly one ordinary continuation, for automatic reflection and manual `/reflect`, including invocation while Pi is idle.
- Preserve the two result types. Do not add `TASK_COMPLETE`, infer completion from `next_step`, or make the observer decide whether ordinary work must execute, wait, ask, or finish.
- Separate the continuation trigger from the reflection's observations. The accepted wake body is exactly `[assistant]\ncontinue`; it remains a synthetic `user`-role control message in both trigger modes.
- Keep the existing reflection report text and formatting unchanged. In ordinary model requests, automatically triggered reports use `assistant`, while reports generated by manual `/reflect` use `user`. Choose the role from recorded trigger origin, not the verdict or report text. Do not add an `[assistant]` title, disclaimer, or plugin label to the reflection body. Verify actual model-facing messages, not just session metadata or TUI rendering.
- Keep original user messages and contextual corrections intact. Store the report outside conversational wake text and reconstruct its trigger-specific projection while the correlated source is retained, including after reload. Built-in compaction bypasses this projection and can omit the report; do not claim zero synthetic user-role content, that generated reports are verbatim human input, or guaranteed summary retention.
- Preserve the XML/report/hook schemas, bounded retries and tool budget, inquiry cleanup, ordinary-work accounting, cooldown, and non-valid-result behavior. No new dependency, user option, Pi-core patch, or notification-consumer coupling is planned.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `conversation-grounded-reflection`: replace the no-issue no-continuation contract with a unified ordinary handoff, require trigger-specific model-facing report roles, and keep the plugin continuation signal distinct.

## Impact

- Runtime handoff and context integration: `src/extension.ts`; extract only a small local helper if source projection otherwise makes that module harder to understand.
- Existing validation: `test/runtime.test.ts`, `test/e2e/stock-pi-fast.test.mjs`, and their existing fixtures. Add source/role assertions at the ordinary provider-request boundary for automatic assistant-role reports and manual user-role reports, including restored contexts, and update the no-extra-request expectation without weakening cooldown coverage.
- Documentation/model alignment: `README.md` and the lifecycle model under `docs/programming-thinking/`, which currently encodes correction-only continuation.
- Public reflection XML remains five fields with two result types; stored version-1 reports remain readable. The `reflection-completed` hook name, values, publication timing, and optional-listener contract remain unchanged.
- Existing conversations are not rewritten or migrated. Only newly generated, correlated watchdog handoffs receive the new projection; other custom messages and old reports retain their compatibility contract. Pi core, `pi-extension-utils`, and custom compaction remain outside scope.
